# DB 학습 로드맵

실무에서 자주 쓰는 것 위주로 정리한다.  
목표: **관계형/비관계형을 구분해서 쓰고, 스키마를 제대로 잡고, 느려지면 원인을 찾고, 로그/대용량을 감당할 수 있게 되기.**

배우고 싶은 것: MySQL, Redis, Elasticsearch  
추가로 추천: PostgreSQL, Kafka, ClickHouse

---

## 왜 이 순서로 배우나

DB는 종류부터 외우면 헷갈린다.  
**저장 방식(관계형/비관계형) → 메인 DB(MySQL) → 빠르게 만드는 법 → 캐시(Redis) → 검색/로그(ES) → 대용량** 순서가 실무랑 맞다.

한 줄로 보면:

```
개념 → MySQL 스키마/SQL → 인덱스/트랜잭션 → Redis 캐시 → ES 검색/로그 → 파티션/복제/대용량
```

역할만 먼저 잡아두면 나중에 안 섞인다.

| 도구 | 역할 | 언제 쓰나 |
|------|------|-----------|
| MySQL (MariaDB) | 메인 데이터. 돈, 회원, 주문처럼 **정합성이 중요한 것** | 거의 모든 서비스의 기본 DB |
| Redis | 메모리 저장소. **캐시, 세션, 락, 카운터** | MySQL이 느릴 때, 자주 읽는 데이터 |
| Elasticsearch | 검색 + 로그 분석 | 상품 검색, 키워드 검색, 서버 로그 조회 |
| PostgreSQL | MySQL과 비슷한 RDB. JSON, 윈도우 함수가 강함 | 분석 쿼리, 복잡한 SQL이 많을 때 |
| Kafka | 로그/이벤트를 **흘려보내는 파이프** | 대용량 로그를 ES나 분석 DB로 보낼 때 |
| ClickHouse | 대용량 분석(OLAP) | 수억 건 로그를 집계할 때 |

지금 쓰는 MariaDB는 MySQL이랑 SQL이 거의 같다.  
학습은 **MySQL 기준으로 하고, 실습은 MariaDB로 해도 된다.**

## 전체 학습 순서 (추천)

기간은 퇴근 후 공부 기준 대략값이다. 빨리 가도 순서는 유지하는 게 좋다.

### 0단계 — 관계형 vs 비관계형 (1~2일)

여기만 확실히 잡으면 나머지가 안 흔들린다.

**관계형 (RDB, SQL)**
- 데이터가 표(테이블)로 들어간다.
- 테이블끼리 키로 연결한다. (회원.id → 주문.user_id)
- 트랜잭션이 있다. 돈/재고처럼 **틀리면 안 되는 데이터**.
- 예: MySQL, MariaDB, PostgreSQL

**비관계형 (NoSQL)**
- 표 구조에 안 맞춰도 된다. 대신 **용도가 갈린다.**
- Key-Value: Redis (키 하나 → 값 하나, 매우 빠름)
- Document: MongoDB (JSON 통째로 저장)
- Search: Elasticsearch (검색/로그에 특화)
- Wide-column: Cassandra, DynamoDB (초대용량 쓰기)

**실무에서 고르는 기준**

```
정합성(주문, 결제, 회원)     → MySQL
자주 읽고, 잠깐 저장         → Redis
검색, 오타, 로그 조회        → Elasticsearch
유연한 JSON 문서             → MongoDB (지금은 후순위)
수억 건 집계/분석            → ClickHouse (나중에)
```

한 서비스에 하나만 쓰지 않는다.  
**MySQL이 본체, Redis가 가속기, ES가 검색/로그** 가 가장 흔한 조합이다.

배울 것
- [ ] ACID가 뭔지 (원자성, 일관성, 격리, 지속성)
- [ ] BASE / eventual consistency 가 뭔지 (NoSQL이 빠른 이유)
- [ ] OLTP vs OLAP (실시간 트랜잭션 vs 분석)
- [ ] 왜 로그를 MySQL에 넣으면 안 되는지

### 1단계 — MySQL 기본 + 올바른 스키마 설계 (2~3주) ★ 가장 중요

속도, 대용량, 캐시 전부 **스키마가 구리면 나중에 막힌다.**  
여기서 시간을 제일 많이 쓰는 게 맞다.

#### 1-1. SQL 기본
- SELECT / INSERT / UPDATE / DELETE
- WHERE, ORDER BY, LIMIT, GROUP BY, HAVING
- JOIN (INNER, LEFT) — 실무는 이 두 개가 거의 전부
- 서브쿼리 vs JOIN
- NULL 다루는 법 (`IS NULL`, `COALESCE`)
- 집계: COUNT, SUM, AVG, MAX/MIN

실습 아이디어
- 회원 / 상품 / 주문 / 주문상세 테이블 만들고 조인으로 매출 뽑기

#### 1-2. 스키마 설계 (정규화)

배울 것
- PK, FK, UNIQUE, NOT NULL, DEFAULT
- 데이터 타입 고르기
  - `INT` vs `BIGINT`
  - `VARCHAR` vs `TEXT` (TEXT는 인덱스/정렬이 불리하다)
  - `DATETIME` vs `TIMESTAMP`
  - `ENUM` 은 나중에 값 추가가 귀찮아서 잘 안 쓰는 편
  - 돈은 `FLOAT` 금지. `DECIMAL` 또는 원 단위 `INT`
- 정규화 1~3정규형
  - 같은 값이 여러 테이블에 중복되지 않게
  - 그런데 **조회가 너무 느리면 일부러 비정규화** 한다 (이름 캐시 컬럼 등)
- 관계: 1:1, 1:N, N:N (중간 테이블)
- 소프트 삭제 (`deleted_at`) vs 하드 삭제
- 생성/수정 시간 (`created_at`, `updated_at`) 습관

스키마 실무 체크리스트
- [ ] PK는 의미 없는 `BIGINT AUTO_INCREMENT` (또는 UUID. 장단점 알고 고르기)
- [ ] FK 컬럼에는 인덱스
- [ ] 상태값은 문자열 남발보다 코드 테이블 or 작은 VARCHAR + 문서화
- [ ] 로그/이력을 본 테이블에 쌓지 않기
- [ ] “나중에 쓸지도” 컬럼을 미리 수십 개 만들지 않기

안티패턴 (자주 보는 실수)
- 한 테이블에 컬럼 100개 (God table)
- 주소, 전화번호, JSON을 VARCHAR에 막 넣기
- EAV (key/value 컬럼으로 뭐든지 저장) — 조회가 지옥이 된다
- 주문 테이블에 상품명을 안 남김 → 상품명 바뀌면 과거 주문서가 같이 바뀜  
  (거래 데이터는 **그 시점 스냅샷**을 남겨야 한다)

#### 1-3. 트랜잭션과 동시성
- COMMIT / ROLLBACK
- Isolation level: READ COMMITTED, REPEATABLE READ (MySQL 기본)
- Dirty read, Non-repeatable read, Phantom read
- 락: 공유락 / 배타락, gap lock, deadlock
- 재고 감소, 잔액 차감 같은 **동시성 문제**를 직접 재현해보기

이 단계 끝 기준
- ERD를 그릴 수 있다
- 주문+재고 트랜잭션을 직접 짜고, 동시에 두 요청이 들어와도 재고가 안 깨진다

### 2단계 — DB 속도 빠르게 하는 법 (2~3주) ★ 실무 핵심

느린 원인은 거의 항상 이 순서다.

```
1. 인덱스 없음 / 인덱스 못 탐
2. 쿼리가 데이터를 너무 많이 읽음 (N+1, SELECT *)
3. 락 대기
4. 커넥션 부족
5. 그다음에야 서버 스펙, 캐시, 샤딩
```

하드웨어부터 올리는 건 마지막이다.

#### 2-1. 인덱스
- B+Tree가 왜 빠른지 (개념만)
- 클러스터드 인덱스 vs 세컨더리 인덱스 (InnoDB는 PK가 클러스터드)
- 복합 인덱스: **왼쪽부터** 탄다 (`(user_id, created_at)` 이면 user_id 없이 created_at만으로는 못 탐)
- 커버링 인덱스
- 인덱스가 안 타는 경우
  - 컬럼에 함수: `WHERE DATE(created_at) = '2026-01-01'`
  - 형변환: VARCHAR 컬럼을 숫자랑 비교
  - `%keyword` 처럼 앞쪽 와일드카드
  - OR 남발, 타입 불일치
- 인덱스 과다의 단점 (INSERT/UPDATE가 느려짐)

#### 2-2. 실행 계획
- `EXPLAIN` / `EXPLAIN ANALYZE`
- type: ALL, index, range, ref, eq_ref, const
- rows, key, Extra (`Using filesort`, `Using temporary`, `Using where`)
- 슬로우 쿼리 로그 (`long_query_time`)

#### 2-3. 쿼리/스키마로 빠르게
- SELECT * 금지. 필요한 컬럼만
- OFFSET 페이지네이션의 한계 → **커서(seek) 페이지네이션**
- JOIN 줄이기 vs 인덱스 잘 타기
- COUNT(*) 가 큰 테이블에서 비싼 이유
- 배치 처리: 한 건씩 INSERT 하지 말고 bulk
- N+1 문제 (앱에서 루프 돌며 쿼리)

#### 2-4. 서버/설정 쪽 (개념)
- 커넥션 풀 (너무 많아도 병목)
- innodb_buffer_pool_size (메모리가 곧 캐시)
- 커넥션 누수 찾기

실습
- 주문 10만 건 넣고, 인덱스 전/후 EXPLAIN 비교
- 슬로우 쿼리 하나 고쳐서 시간 줄어든 걸 기록

이 단계 끝 기준
- 느린 API가 오면 EXPLAIN 보고 “인덱스가 없어서” / “풀스캔” 을 말로 설명할 수 있다

### 3단계 — Redis (1~2주)

MySQL을 빠르게 만드는 다음 수단이 캐시다.  
Redis를 DB 대체품으로 쓰면 안 된다. **날아갈 수 있는 데이터**에 쓴다.

배울 것
- 자료구조: String, Hash, List, Set, Sorted Set
- TTL (만료). 캐시는 반드시 만료 또는 무효화 전략이 있어야 한다
- 캐시 패턴
  - Cache-Aside (앱이 먼저 Redis 보고, 없으면 DB)
  - Write-through / Write-behind (개념)
- 캐시 스탬피드, 캐시 penetration (없는 키를 계속 물어봄)
- 세션 저장
- 분산 락 (`SETNX` / Redisson 같은 것)
- 랭킹: Sorted Set
- Pub/Sub (실시간 알림 — 나중에)
- persistence: RDB / AOF (꺼지면 얼마나 남나)

실무 사용처
- 로그인 세션, JWT 블랙리스트
- 상품 상세/설정값처럼 자주 읽는 것
- 좋아요 수, 조회수 (나중에 DB에 주기적으로 반영)
- Rate limit (초당 요청 제한)
- 중복 클릭 방지 락

주의
- Redis에 회원/주문 원본을 두고 “이게 메인 DB” 로 쓰지 말 것
- 큰 키 하나, 큰 컬렉션 하나에 몰아넣으면 Redis도 느리다
- 메모리 한도 생각하기 (`maxmemory`, eviction 정책)

이 단계 끝 기준
- 게시글 목록을 Redis 캐시 + TTL 로 만들고, 수정 시 캐시 삭제까지 한다

### 4단계 — Elasticsearch (2~3주) — 검색 + 로그 분석

MySQL `LIKE '%키워드%'` 는 데이터가 커지면 죽는다.  
검색이랑 로그 조회는 ES 영역이다.

#### 4-1. 검색 엔진으로
- 인덱스 / 도큐먼트 / 필드 (MySQL의 DB / row / column 이라고 보면 대충 맞다)
- inverted index 가 왜 검색이 빠른지
- analyzer, tokenizer (한글: nori)
- match vs term
- 필터, aggregation (집계)
- mapping (스키마). dynamic mapping 만 믿으면 나중에 사고 난다
- MySQL → ES 동기화 전략
  - 앱에서 둘 다 쓰기
  - 주기적 배치
  - binlog/CDC (나중에)

실습
- 상품명/설명 검색, 오타 허용, 카테고리 필터, 가격 범위

#### 4-2. 로그 데이터 분석 (원하던 것)

실무 파이프라인은 보통 이렇다.

```
앱/서버 로그 → Filebeat 또는 앱에서 직접 전송
           → (선택) Logstash / Kafka
           → Elasticsearch
           → Kibana 로 조회
```

배울 것
- ELK / Elastic Stack: Elasticsearch + Logstash + Kibana
- 구조화 로그 (JSON 로그가 산 로그보다 분석이 쉽다)
- 인덱스 생명주기: 날짜별 인덱스 (`logs-2026.09.09`), ILM, 오래된 로그 삭제
- 로그를 MySQL에 넣지 않는 이유
  - 쓰기 폭주, 인덱스 비대화, 백업 지옥, 분석 쿼리가 OLTP를 잡아먹음
- Kibana Discover / Visualization
- 자주 보는 분석
  - 에러 급증 시각
  - 느린 API URL
  - 특정 유저/IP 추적
  - 상태코드 4xx/5xx 비율

이 단계 끝 기준
- 샘플 로그를 ES에 넣고 Kibana에서 “어제 5xx 많은 API” 를 찾아낸다
- 상품 검색 API를 MySQL LIKE 가 아니라 ES로 바꾼다

### 5단계 — 대용량 데이터 처리 (2~4주)

데이터가 “좀 많다”와 “진짜 대용량”은 대응이 다르다.

#### 5-1. MySQL에서 먼저 버티기 (대부분 여기로 충분)
- 파티셔닝 (날짜 범위 파티션이 실무에서 제일 많음)
- 아카이빙: 오래된 주문을 히스토리 테이블/다른 저장소로
- 읽기 부하: Replica (Master-Slave, Source-Replica)
- 쓰기/읽기 분리 시 **replica lag** 주의
- 배치 잡으로 집계 테이블 미리 만들어 두기 (매일 매출 요약)
- 대량 INSERT/DELETE 는 쪼개서 (락, binlog, undo 폭발 방지)

#### 5-2. 그다음 스케일 아웃
- 샤딩 (user_id 해시로 DB 나누기) — 운영 비용이 커서 최후 수단
- 큐로 쓰기 부하 평탄화 (주문 생성 → 큐 → 워커)

#### 5-3. 로그/이벤트 대용량
- Kafka: 로그를 ES에 직접 때리지 않고 버퍼로 받기
- 로그는 저장과 분석을 분리
  - 원본: S3 / 오브젝트 스토리지
  - 최근 N일 조회: ES
  - 장기 집계: ClickHouse 또는 데이터 웨어하우스

대용량에서 스키마가 다시 중요해지는 지점
- 파티션 키를 뭘로 할지 (날짜? 유저?)
- 핫 데이터 / 콜드 데이터 분리
- “전체 테이블 COUNT” 같은 쿼리를 서비스에서 쓰지 않기

이 단계 끝 기준
- 월 단위 파티션 테이블을 만들고, 오래된 파티션 drop 을 해본다
- “슬로우 로그 분석 → 인덱스 → 캐시 → 리드 레플리카” 순서로 튜닝 우선순위를 말할 수 있다

## 추가로 추천하는 것 (우선순위)

지금 세 개(MySQL, Redis, ES)가 **백엔드 실무 기본 세트**다.  
다 잡은 뒤에 아래를 보면 된다.

| 순위 | 무엇 | 이유 |
|------|------|------|
| 1 | PostgreSQL | MySQL 다음으로 공고가 많다. 윈도우 함수, JSON, CTE가 강력해서 **분석/복잡한 쿼리**에 좋다. MySQL 하고 나면 이전이 쉽다. |
| 2 | Kafka | 로그/이벤트 파이프라인의 표준. ES만 있으면 “검색”은 되지만, **대용량 로그 수집**은 Kafka가 받쳐줘야 한다. |
| 3 | ClickHouse | 로그·행동 데이터 **집계**가 ES보다 훨씬 싸다/빠르다. “로그 분석”을 진짜 데이터 분석까지 밀 때. |
| 4 | MongoDB | 문서형 NoSQL 감을 익히기엔 좋지만, 검색은 ES, 메인 데이터는 MySQL인 팀이 많다. 급하지 않음. |
| 후순위 | DynamoDB, Cassandra | AWS/초대용량 특화. 서비스 규모가 커지거나 클라우드 공고 볼 때. |

안 배워도 되는 것 (지금은)
- Oracle 전용 SQL — 회사 가면 그때
- Graph DB, Time-series 전부 — 필요해지면
- ORM만 만지고 SQL을 안 보는 것 — 튜닝이 안 된다. ORM 쓰더라도 SQL은 직접 봐야 한다.

## 실무에서 자주 나오는 조합

백엔드 API 서버 기준으로 가장 많이 보는 그림:

```
클라이언트
    ↓
API 서버
    ├─ MySQL     : 회원, 주문, 결제 (진실의 원천)
    ├─ Redis     : 세션, 캐시, 락
    └─ ES        : 상품 검색, 관리자 로그 조회

서버 로그 ──(Filebeat/Kafka)──▶ ES ──▶ Kibana
오래된 로그 ──────────────▶ S3 / ClickHouse
```

의사결정 연습 문제 (면접/실무 둘 다 나옴)
- 조회수 저장을 MySQL로? Redis로? 왜?
- 상품 검색을 MySQL FULLTEXT vs ES?
- 주문 로그 1년치를 사용자에게 보여줘야 하면 테이블을 어떻게 쪼개나?
- 재고 동시 주문 100건이면 락을 어디에 걸까?

## 공부할 때 방법

1. **설치보다 쿼리.** 도커로 MySQL/Redis/ES 띄우고 바로 SELECT 부터.
2. **가짜 데이터 많이.** 100건에서는 인덱스가 이득인지 안 보인다. 최소 10만 건.
3. **매번 EXPLAIN.** 감으로 인덱스 달지 말고 실행 계획으로 확인.
4. **노트는 삽질 위주.** 이 폴더에 `왜 느렸는지`, `인덱스 전후` 를 남기는 게 문법 정리보다 가치 있다.
5. ORM을 쓰더라도 **실제 SQL 로그**를 켠다. N+1은 여기서 보인다.

추천 실습 미니 프로젝트 (하나면 충분)
- 쇼핑몰 백엔드 작은 버전
  - MySQL: 회원, 상품, 주문
  - Redis: 상품 상세 캐시, 재고 락
  - ES: 상품 검색 + 주문/에러 로그 조회
