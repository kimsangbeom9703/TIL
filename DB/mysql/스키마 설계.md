# [DB] MySQL 스키마 설계

로드맵 1단계. 속도, 캐시, 대용량보다 **테이블을 어떻게 쪼개고 무슨 타입으로 넣을지**가 먼저다.  
스키마가 구리면 인덱스도, Redis도 나중에 막힌다.

---

## 스키마가 뭐냐

```
    테이블 이름, 컬럼, 타입, 제약(PK/FK/UNIQUE/NOT NULL),
    테이블끼리 관계까지 포함한 "데이터 설계도"다.

    코드로 치면 클래스 설계랑 같다.
    필드 대충 넣으면 나중에 리팩터링이 지옥인 것처럼
    테이블 대충 만들면 ALTER 가 지옥이다.

    앱은 배포로 고치기 쉬운데
    이미 쌓인 수천만 행은 쉽게 못 고친다.
    그래서 처음부터 좀 고민한다.
```

설계할 때 항상 묻는 질문 세 개

```
    1.  이 값은 어디에 한 번만 있으면 되나, 여러 군데 있어야 하나
    2.  이 값은 나중에 바뀌면 과거 기록도 같이 바뀌어도 되나
    3.  이 조건으로 자주 찾을 건가 (그러면 컬럼이 필요하고 인덱스도 필요)
```

2번이 핵심이다.  
상품 이름은 바뀌어도 되지만, **이미 나간 주문서의 상품 이름**은 그 시점 그대로여야 한다.

## 실무에서 테이블 하나 만들 때 기본 뼈대

```sql
CREATE TABLE users (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    email         VARCHAR(255)    NOT NULL,
    name          VARCHAR(50)     NOT NULL,
    status        VARCHAR(20)     NOT NULL DEFAULT 'active',
    created_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                                  ON UPDATE CURRENT_TIMESTAMP(3),
    deleted_at    DATETIME(3)     NULL DEFAULT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_email (email),
    KEY idx_users_status (status)
);
```

거의 모든 테이블에 반복되는 것

| 컬럼 | 이유 |
|------|------|
| `id` | 의미 없는 PK. 주민번호, 이메일을 PK로 쓰지 않는다. 값이 바뀔 수 있다. |
| `created_at` | 언제 생겼는지. 장애 추적, 통계, 커서 페이지네이션에 쓴다. |
| `updated_at` | 마지막 수정. 캐시 무효화, 동기화 기준이 된다. |
| `deleted_at` | 소프트 삭제. NULL 이면 살아 있는 행. |

`DATETIME(3)` 의 `(3)` 은 밀리초다.  
같은 초에 여러 건이 들어가면 정렬이 꼬일 수 있어서 넣는 편이다.

엔진은 안 적으면 기본이 InnoDB 다. 메인 테이블은 그냥 InnoDB 로 둔다.

```sql
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

## PK / FK / UNIQUE / NOT NULL

### PK (Primary Key)

```
    행 하나를 가리키는 번호.

    InnoDB 는 PK 순서로 디스크에 쌓는다 (클러스터드 인덱스).
    그래서 PK 는
        - 값이 안 바뀌고
        - 최대한 순차 증가하고
        - 짧을수록
    유리하다.

    BIGINT AUTO_INCREMENT 가 기본 선택이다.

    UUID 를 PK 로 쓰면
        - 분산 시스템에서 ID 충돌이 없고
        - 외부에 순번을 안 보여 줘서 좋지만
        - 랜덤 값이라 삽입 위치가 흩어져서 큰 테이블에서 느려질 수 있다.

    외부에 id 를 보여주고 싶지 않으면
    PK 는 BIGINT 로 두고, 공개용 코드는 별도 컬럼 (order_no 같은 것) 으로 둔다.
```

INT vs BIGINT

```
    INT UNSIGNED 최대 약 42억.
    로그, 주문, 조회수 이벤트는 금방 넘는다.
    메인 테이블 PK 는 그냥 BIGINT 로 시작한다.
    나중에 INT → BIGINT 변경이 진짜 고통이다.
```

### FK (Foreign Key)

```
    다른 테이블의 PK 를 가리킨다.
    users.id  ←  orders.user_id

    FK 를 걸면
        - 없는 회원에게 주문이 생기는 걸 막는다
        - 회원 지울 때 주문을 어떻게 할지 (RESTRICT / CASCADE) 를 정한다

    실무에선
        ON DELETE RESTRICT  또는  SET NULL 을 많이 쓴다.
        CASCADE 는 회원 하나 지웠더니 주문/결제/리뷰가 다 날아갈 수 있어서
        메인 데이터에는 잘 안 건다.

    FK 컬럼에는 반드시 인덱스가 있어야 한다.
    MySQL 은 FK 만들 때 인덱스가 없으면 알아서 만들기도 하지만
    이름을 내가 정하는 게 나중에 보기 좋다.
```

```sql
CONSTRAINT fk_orders_user
    FOREIGN KEY (user_id) REFERENCES users (id)
    ON DELETE RESTRICT
    ON UPDATE RESTRICT
```

앱에서만 관계를 보장하고 DB FK 를 빼는 팀도 있다.  
마이그레이션, 대량 삭제, 샤딩이 쉬워지는 대신 **잘못된 데이터가 들어갈 구멍**이 생긴다.  
처음 배울 때는 FK 를 걸고, 왜 빼는지 이해한 뒤에 빼는 게 맞다.

### UNIQUE / NOT NULL / DEFAULT

```
    NOT NULL
        "이 값은 비어 있으면 데이터가 아니다"
        email, 주문상태, 가격 같은 건 NULL 을 허용하지 않는다.

        NULL 은 "값 없음" 과 "아직 모름" 이 섞여서
        쿼리 실수가 잘 난다.
            WHERE status != 'active'   ← status 가 NULL 인 행은 안 나온다

    UNIQUE
        이메일은 회원 테이블에서 하나여야 한다.
        소프트 삭제를 쓰면 탈퇴한 이메일 재가입이 막힐 수 있다.
        그때는 (email, deleted_at) 유니크 같은 우회가 필요해서
        처음부터 정책을 정한다.

    DEFAULT
        상태값, 생성시각처럼 "안 넣으면 이 값" 을 서버/앱 양쪽에서 안 맞춰도 되게.
```

## 데이터 타입 고르기

타입은 "대충 VARCHAR(255)" 가 아니다.  
저장 공간, 인덱스 크기, 비교 방식, 잘못된 값 방지까지 타입으로 한다.

### 숫자

```
    TINYINT     0~255 (UNSIGNED).  상태 코드, boolean 대용 (0/1)
    INT         일반 카운트, 재고.  단 PK 는 BIGINT 권장
    BIGINT      PK, 주문번호 내부 id, 큰 카운트
    DECIMAL     돈, 환율, 소수점 오차 나면 안 되는 것
    FLOAT/DOUBLE  쓰지 말 것.  0.1 + 0.2 문제가 돈에서 난다
```

돈은 둘 중 하나로 통일한다.

```
    1.  DECIMAL(12, 2)   원 단위 소수점 2자리 (달러 등)
    2.  INT/BIGINT       원을 정수로.  12000 원 → 12000

    한국 서비스면 원 단위 BIGINT 도 많이 쓴다.
    중요한 건 테이블마다 섞지 않는 것.
```

### 문자열

```
    CHAR(n)       길이 고정.  국가코드 KR, 성별 M/F 정도
    VARCHAR(n)    거의 전부 이거.  n 은 실제 최대에 가깝게
    TEXT          본문, 로그 메시지, 긴 설명

    VARCHAR vs TEXT
        - TEXT 는 기본 인덱스를 못 달거나 prefix 만 가능
        - ORDER BY / GROUP BY 에 불리할 수 있다
        - "가끔 길다" 싶어도 255~1000 이면 VARCHAR
        - 게시글 본문, HTML, JSON 큰 덩어리만 TEXT

    VARCHAR(255) 를 습관처럼 쓰지 말 것.
    이름 50, 휴대폰 20, 우편번호 10 처럼 의미 있는 길이를 준다.
    인덱스는 컬럼 길이만큼 메모리를 먹는다.
```

문자셋

```
    지금 만들면 utf8mb4 + utf8mb4_unicode_ci (또는 0900_ai_ci)

    utf8 (utf8mb3) 는 이모지, 일부 한글 보조문자가 깨진다.
    MySQL 의 utf8 은 3바트라서 이모지가 안 들어간다.
```

### 날짜

```
    DATE            생일, 영업일.  시간 필요 없으면 DATE
    DATETIME        주문시각, 로그시각.  타임존 변환을 앱이 한다
    TIMESTAMP       UTC 로 저장되고 세션 타임존으로 보여 준다
                    2038 문제 (구버전), 서버 타임존 설정에 민감

    실무 추천
        - 비즈니스 시각은 DATETIME(3) 으로 통일
        - 서버/DB/앱 타임존을 UTC 로 맞추고
          보여줄 때만 KST 로 바꾼다

    "날짜만 비교" 하려고
        WHERE DATE(created_at) = '2026-09-09'
    이렇게 함수를 씌우면 인덱스가 안 탄다.

        WHERE created_at >= '2026-09-09 00:00:00'
          AND created_at <  '2026-09-10 00:00:00'
    이렇게 범위로 쓴다.
```

### 상태값 / boolean / JSON

```
    BOOLEAN
        MySQL 에선 TINYINT(1) 이다.  그냥 TINYINT 로 봐도 된다.

    ENUM('active','dormant')
        값 추가할 때 ALTER 가 필요하고, 앱/DB 가 이중으로 관리된다.
        VARCHAR(20) + 앱 상수, 또는 코드 테이블을 더 많이 쓴다.

    JSON
        설정값, 가변 속성, 외부 API 원본 응답처럼
        "구조가 자주 바뀌는 덤프" 에 쓴다.

        JSON 안에 넣은 값으로 매일 검색/조인하면 설계가 잘못된 거다.
        자주 찾는 값은 꺼내서 컬럼으로 승격한다.
```

### 전부 VARCHAR 로 쓰면 안 되나

된다. 프로토타입에서 숫자·날짜까지 VARCHAR 로 찍는 건 가능하다.  
다만 **나중에 느려지고, 값이 틀어지고, 인덱스가 안 탄다.** 그래서 실무에서는 안 한다.

VARCHAR 는 “글자를 넣는 칸”이다. 숫자·날짜·돈도 글자로 넣으면 MySQL 이 그걸 숫자/날짜로 이해를 못 한다.

**정렬이 글자순이 된다**

```sql
-- 가격을 VARCHAR 로 넣으면 ORDER BY price 결과가
20
100
3

-- 숫자 크기순이 아니라 글자순이다.
100
20
3
-- '1' 이 '2' 보다 앞이라 100 이 20 보다 앞에 온다.

-- CAST(price AS UNSIGNED) 를 붙이면 그때마다 변환해서 인덱스도 못 탄다.
```

**계산이 이상해진다**

```
    '1000' + '2000'      운 좋으면 3000
    '1,000' + '2000'     콤마 때문에 1 만 더해지거나 0
    '2026-09-09' + 1     날짜 더하기가 안 된다

    돈·재고·수량은 타입 자체가 계산용이어야 한다.
```

**범위 조회가 비싸지거나 틀린다**

```sql
-- DATETIME 이면 인덱스 타고 범위 스캔
WHERE created_at >= '2026-09-01'
  AND created_at <  '2026-10-01'

-- VARCHAR 에 '2026-09-09 13:00:00' 을 넣어두면
-- 포맷이 하나라도 다를 때 (9/9, 2026.09.09) 글자 비교가 되고
-- 인덱스 효과가 없거나 결과가 틀린다.
```

**JOIN 에서 형변환이 난다**

```sql
-- users.id 는 BIGINT, orders.user_id 를 VARCHAR 로 만들면
ON o.user_id = u.id

-- 매 행마다 문자열 ↔ 숫자 변환.
-- 이 변환 때문에 인덱스를 못 타는 경우가 많다.

-- PK / FK 는 양쪽 타입을 같게 둔다.
```

**칸이 쓸데없이 커진다**

```
    status, gender, Y/N 까지 VARCHAR(255) 로 두면
        - 행이 뚱뚱해져서 한 페이지에 적게 들어간다 → IO 증가
        - 인덱스도 컬럼 길이만큼 먹는다
        - 'active ', 'Active', 'ACTIVE' 가 서로 다른 값이 된다

    상태값은 VARCHAR(20) 이면 충분하다.
    글자면 VARCHAR, 숫자면 숫자 타입, 시각이면 DATETIME.
```

한 줄 정리

| 값 | VARCHAR 만 쓸 때 | 맞는 타입 |
|----|------------------|-----------|
| id, 개수, 재고 | 정렬/계산 꼬임 | `BIGINT` / `INT` |
| 돈 | `'1000'+'20'` 사고 | `BIGINT`(원) 또는 `DECIMAL` |
| 주문시각 | 포맷 제각각, 범위 검색 실패 | `DATETIME(3)` |
| 이메일, 이름, 상품명 | 원래 글자 | `VARCHAR(적당한 길이)` |
| 게시글 본문 | VARCHAR 최대 길이가 부족할 수 있음 | `TEXT` |
| 상태값 | 255 는 과함 | `VARCHAR(20)` |

## 테이블 엔진(타입)이랑 성능

MySQL 에서 “테이블 타입” 은 보통 `ENGINE=InnoDB` 같은 **스토리지 엔진**을 말한다.  
컬럼 타입도 성능에 영향을 주지만, **체감이 큰 쪽은 엔진**이다. 틀린 컬럼 타입(`TEXT`/`JSON`/`FLOAT` 오용)은 그다음이다.

### 엔진 — 차이가 크다

지금 만들면 **InnoDB 만 쓰면 된다.** 나머지는 용도가 다르다.

| 엔진 | 특징 | 성능 / 실무 |
|------|------|-------------|
| **InnoDB** (기본) | 트랜잭션, FK, 행 단위 락, PK 순서로 데이터 저장 | 회원/주문/결제 전부 이거 |
| **MyISAM** | 트랜잭션 없음, **테이블 통째 락** | 예전에 SELECT 가 조금 빠르다는 말이 있었음. 동시 쓰기면 바로 병목. 지금은 안 씀 |
| **MEMORY** | 메모리에만 존재. 재시작 시 증발 | 임시 계산, 초고속 조회용. 메인 데이터 금지 |
| **ARCHIVE** | 압축, INSERT/SELECT 만 | 아주 오래된 로그 보관. 업데이트 불가 |
| **CSV** | 진짜 CSV 파일 | 디버깅용. 느림 |

성능이 갈리는 지점

```
    락 범위
        InnoDB  → 그 행만 잠근다.  주문이 동시에 들어와도 버틴다.
        MyISAM  → 테이블 전체를 잠근다.  한 명이 쓰는 동안 나머지는 대기.

    트랜잭션
        InnoDB  → COMMIT / ROLLBACK.  재고 차감이 중간에 죽어도 복구 가능.
        MyISAM  → 없다.  반만 저장된 주문이 남는다.

    PK 저장 방식 (InnoDB)
        데이터 자체가 PK 순서로 붙어 있다.
        WHERE id = 123 은 빠르고,
        PK 가 랜덤 UUID 면 삽입 위치가 흩어져서 큰 테이블에서 느려질 수 있다.
```

엔진 확인

```sql
SHOW TABLE STATUS FROM shop;
-- Engine 컬럼이 InnoDB 인지 보면 된다.

SHOW CREATE TABLE orders;
```

이미 InnoDB 면 엔진 선택은 끝난 거다.  
그다음 튜닝은 인덱스와 쿼리가 읽는 양이다.

### 컬럼 타입 — 차이는 나지만 “틀린 선택”이 문제

같은 InnoDB 라도 타입이 뚱뚱하면 인덱스·메모리가 커져서 느려진다.  
다만 인덱스 없는 풀스캔 옆에 두면 타입 차이는 티가 잘 안 난다.

```
    INT vs BIGINT
        INT 4바이트, BIGINT 8바이트.
        PK/FK/인덱스에 곱해지면 메모리·디스크가 커진다.
        그래도 주문 PK 를 INT 로 시작했다가 42억 넘기는 사고보다는 BIGINT 가 맞다.
        성능 때문에 INT 쓰는 건 status, quantity 같은 작은 값.

    VARCHAR vs TEXT
        실무에서 제일 자주 터진다.
        VARCHAR 는 행 안에 들어가고 인덱스도 달기 쉽다.
        TEXT 는 큰 값이 페이지 밖에 저장되고, 인덱스·정렬이 불리하다.
        상품명, 이메일은 VARCHAR. 게시글 본문만 TEXT.

    CHAR vs VARCHAR
        CHAR(10) 은 항상 10글자 공간을 쓴다 (패딩).
        국가코드 KR 처럼 길이가 고정이면 CHAR 가 조금 이득일 수 있다.
        이름은 VARCHAR.

    FLOAT vs DECIMAL / 정수
        FLOAT 는 빠르지만 돈이 틀린다. 속도 이득보다 사고가 크다.
        금액 연산은 DECIMAL 이 INT 보다 조금 느리다. 그래도 돈은 DECIMAL 또는 원 단위 정수.

    JSON vs 컬럼
        JSON 에서 price 를 꺼내서 매일 검색하면 일반 컬럼보다 확실히 느리다.
        자주 찾는 값은 컬럼으로 빼고, JSON 은 가끔 보는 덤프만.

    ENUM
        내부는 정수라 저장은 작다.
        값 추가할 때 ALTER 가 필요하고, 앱이랑 스키마가 이중 관리된다.
        성능 때문에 ENUM 쓰기보다 VARCHAR(20) + 인덱스가 유지보수에 이득인 경우가 많다.

    NULL vs NOT NULL
        NULL 허용이면 행마다 NULL 비트맵이 생긴다. 차이는 작다.
        진짜 문제는 WHERE status != 'active' 할 때 NULL 행이 빠지는 쿼리 실수 쪽.
```

느린 원인 우선순위 (다시)

```
    1. 인덱스 없음 / 풀스캔           ← 압도적 1등
    2. 필요한 것보다 넓은 행을 읽음    ← SELECT *, TEXT/JSON 이 목록에 딸려옴
    3. 락 대기 (엔진/트랜잭션)
    4. 컬럼이 쓸데없이 큼             ← VARCHAR(255) 남발, TEXT 오용
    5. INT 대신 BIGINT 쓴 것          ← 거의 티 안 남
```

한 줄

```
    엔진: 메인 테이블은 InnoDB. MyISAM 은 동시성에서 진다.
    컬럼 타입: 차이는 나지만 TEXT/JSON/FLOAT 오용이 아니면 미세한 편.
    체감 성능: 타입 미세 조정 < 인덱스 + 쿼리가 읽는 양.
```

## 관계: 1:1, 1:N, N:N

쇼핑몰로 보면 거의 다 나온다.

```
    users  1 : N  orders          회원 한 명이 주문 여러 개
    orders 1 : N  order_items     주문 하나에 상품 여러 줄
    users  1 : 1  user_profiles   회원 상세(주소록, 마케팅 수신)를 본 테이블에서 분리
    products N : N  tags          상품-태그.  중간 테이블 필요
```

### 1:N (가장 많음)

```sql
-- 자식이 부모 id 를 가진다
CREATE TABLE orders (
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id    BIGINT UNSIGNED NOT NULL,
    ...
    PRIMARY KEY (id),
    KEY idx_orders_user_id (user_id),
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id) REFERENCES users (id)
);
```

질문: "누가 누구를 여러 개 가지나?"  
여러 개를 가지는 쪽이 **자식**이고, 자식에 `부모_id` 가 붙는다.

### 1:1

```
    한 테이블에 다 넣어도 된다.
    굳이 나누는 이유
        - 큰 TEXT/JSON 을 목록 조회할 때마다 안 읽고 싶을 때
        - 민감정보 (CI, 계좌) 접근 권한을 테이블 단위로 나눌 때
        - 대부분 비어 있는 컬럼이 많을 때

    PK 를 부모와 같게 가져가기도 한다. (user_id 가 PK 이자 FK)
```

### N:N

```sql
CREATE TABLE products (
    id    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    name  VARCHAR(200)    NOT NULL,
    PRIMARY KEY (id)
);

CREATE TABLE tags (
    id    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    name  VARCHAR(50)     NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_tags_name (name)
);

-- 중간 테이블. N:N 의 실체다.
CREATE TABLE product_tags (
    product_id  BIGINT UNSIGNED NOT NULL,
    tag_id      BIGINT UNSIGNED NOT NULL,
    created_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (product_id, tag_id),
    KEY idx_product_tags_tag_id (tag_id),
    CONSTRAINT fk_product_tags_product
        FOREIGN KEY (product_id) REFERENCES products (id),
    CONSTRAINT fk_product_tags_tag
        FOREIGN KEY (tag_id) REFERENCES tags (id)
);
```

중간 테이블에 나중에 `display_order` 같은 컬럼이 붙는 일이 많다.  
그래서 "id 없는 연결만" 으로 시작해도, 의미 있는 데이터가 생기면 독립 테이블로 본다.

## 정규화 — 같은 값을 여러 곳에 두지 않기

정규화는 교과서 용어보다 **중복을 어디로 몰 것인가** 다.

### 1정규형
한 칸에 값 하나.  
`phone = '010-1111, 010-2222'` 금지. 전화번호 테이블로 분리하거나 컬럼을 나눈다.

### 2정규형
PK 일부에만 의존하는 컬럼을 빼다.  
주문상세에 `product_id, product_name, product_price, category_name` 을 다 넣고  
카테고리명을 상품마다 중복 저장하는 식.

### 3정규형
PK 가 아닌 컬럼에 또 의존하는 값을 빼다.  
`users` 에 `zipcode, address, city` 가 있고 city 가 zipcode 로 결정되면 중복 후보다.

실무 한 줄

```
    마스터 데이터 (회원, 상품, 카테고리)
        → 정규화한다.  이름은 한곳만 고친다.

    거래 데이터 (주문, 결제, 계약)
        → 그 순간 스냅샷을 남긴다.  일부러 중복한다.
```

이게 정규화를 깨는 게 아니라 **올바른 비정규화** 다.

나쁜 예

```sql
-- 주문 상세에 product_id 만 있음
-- 석 달 뒤 상품명을 "겨울 패딩" → "겨울 패딩 리뉴얼" 로 바꾸면
-- 지난 주문서도 같이 바뀐다.  고객 영수증과 안 맞는다.
```

좋은 예

```sql
CREATE TABLE order_items (
    id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_id       BIGINT UNSIGNED NOT NULL,
    product_id     BIGINT UNSIGNED NULL,          -- 상품이 삭제돼도 주문은 남아야 해서 NULL 허용하는 팀도 있음
    product_name   VARCHAR(200)    NOT NULL,      -- 주문 당시 이름
    unit_price     BIGINT          NOT NULL,      -- 주문 당시 가격 (원)
    quantity       INT             NOT NULL,
    PRIMARY KEY (id),
    KEY idx_order_items_order_id (order_id)
);
```

`product_id` 는 "어느 상품이었는지" 추적,  
`product_name` / `unit_price` 는 "그때 무엇이 얼마였는지" 기록.

## 소프트 삭제 vs 하드 삭제

```
    하드 삭제
        DELETE FROM users WHERE id = 1
        단순하다.  그런데 주문 FK, 로그, "누가 샀나" 가 끊긴다.
        GDPR/개인정보 파기 요청처럼 진짜 지워야 할 때 쓴다.

    소프트 삭제
        UPDATE users SET deleted_at = NOW(3) WHERE id = 1
        조회할 때마다 deleted_at IS NULL 을 빼먹는 실수가 난다.
        UNIQUE(email) 이면 탈퇴 후 같은 이메일 재가입이 막힌다.

    선택 기준
        - 돈/법적 기록 (주문, 결제, 계약): 사실상 삭제 안 함.  상태만 변경
        - 회원: 소프트 삭제 + 개인정보 마스킹 후 일정 기간 뒤 하드 삭제
        - 임시 데이터, 캐시성 테이블: 하드 삭제
```

상태 컬럼과 삭제를 섞지 말 것.

```
    status = 'withdrawn'  과  deleted_at  둘 다 있으면
    조회 조건이 팀마다 달라진다.
    하나는 메인으로 정한다.
```

```
        last_login_at, last_login_ip, login_count,
        memo, admin_memo, profile_json, ...
    를 계속 추가하면 God table 이 된다.

    자주 안 쓰는 큰 필드, 계속 쌓이는 이력은 테이블을 나눈다.

        users              현재 상태만
        user_login_logs    로그인 이력 (나중엔 ES)
```

```
    3.  로그성 대량은 MySQL 이 아니라 ES / 파일 / S3
```

## 자주 보는 안티패턴

### 1. God table
컬럼 80~100개짜리 `users`.  
목록 조회에 본문/JSON 이 딸려 나와서 느려진다. 책임이 다른 것은 테이블을 가른다.

### 2. EAV (entity-attribute-value)

```sql
-- 이러면 "20대 서울 회원" 같은 조회가 조인 지옥이다
CREATE TABLE user_attrs (
    user_id   BIGINT,
    attr_key  VARCHAR(50),   -- 'age', 'city', ...
    attr_val  VARCHAR(255)
);
```

유연해 보이지만 타입도 없고 인덱스도 못 믿게 된다.  
진짜 가변 속성은 JSON 한 컬럼 + 자주 찾는 키만 컬럼으로 빼는 쪽이 낫다.

### 3. 컬럼에 리스트를 문자열로

```
    category_ids = '1,5,17'
    WHERE FIND_IN_SET(5, category_ids)
    인덱스 불가. N:N 중간 테이블로.
```

### 4. 미리 만드는 예비 컬럼

```
    spare1, spare2, extra_field, col01 ...
    의미 없는 컬럼은 쓰는 사람도 모른다.
    필요할 때 ALTER 로 추가한다. (온라인 DDL 가능한 버전이면 더 부담이 적다)
```

### 5. 이름만 다른 같은 테이블

```
    orders_2024, orders_2025 를 앱에서 UNION
    → 파티셔닝이나 아카이브 정책으로 나중에 푼다.
    처음부터 연도별 테이블을 수동으로 쪼개지 말 것.
```

### 6. 전부 VARCHAR(255)

```
    id, 가격, 날짜, 상태까지 전부 VARCHAR 로 두면
        - 가격 정렬이 글자순이 된다 (100 이 20 앞에)
        - 날짜 범위 검색이 깨지거나 인덱스를 못 탄다
        - PK/FK 타입이 달라서 JOIN 때 형변환이 난다
        - 행과 인덱스만 쓸데없이 커진다

    글자만 VARCHAR. 숫자는 숫자 타입, 시각은 DATETIME.
```

### 7. 메인 테이블을 MyISAM 으로

```
    테이블 통째 락 + 트랜잭션 없음.
    동시 주문이 들어오면 대기하고, 중간 장애 시 반만 저장된 주문이 남는다.
    메인 데이터는 InnoDB.
```

## 미니 쇼핑몰 스키마 예시

로드맵 실습용. 회원 / 상품 / 주문 / 주문상세.

```sql
CREATE DATABASE shop DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE shop;
-- ENGINE 생략해도 기본은 InnoDB. 메인 테이블은 InnoDB 로 둔다.

CREATE TABLE users (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    email         VARCHAR(255)    NOT NULL,
    name          VARCHAR(50)     NOT NULL,
    status        VARCHAR(20)     NOT NULL DEFAULT 'active',  -- active, dormant, withdrawn
    created_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                                  ON UPDATE CURRENT_TIMESTAMP(3),
    deleted_at    DATETIME(3)     NULL DEFAULT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_email (email),
    KEY idx_users_status (status)
);

CREATE TABLE products (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    name          VARCHAR(200)    NOT NULL,
    price         BIGINT          NOT NULL,          -- 원
    stock         INT             NOT NULL DEFAULT 0,
    status        VARCHAR(20)     NOT NULL DEFAULT 'on_sale', -- on_sale, sold_out, hidden
    created_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                                  ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    KEY idx_products_status (status),
    KEY idx_products_name (name)
);

CREATE TABLE orders (
    id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_no        VARCHAR(30)     NOT NULL,         -- 외부 노출용. PK 가 아님
    user_id         BIGINT UNSIGNED NOT NULL,
    status          VARCHAR(20)     NOT NULL DEFAULT 'paid', -- paid, cancelled, refunded
    total_amount    BIGINT          NOT NULL,
    ordered_at      DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    created_at      DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at      DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                                    ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_orders_order_no (order_no),
    KEY idx_orders_user_id (user_id),
    KEY idx_orders_ordered_at (ordered_at),
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id) REFERENCES users (id)
        ON DELETE RESTRICT
);

CREATE TABLE order_items (
    id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_id       BIGINT UNSIGNED NOT NULL,
    product_id     BIGINT UNSIGNED NOT NULL,
    product_name   VARCHAR(200)    NOT NULL,          -- 스냅샷
    unit_price     BIGINT          NOT NULL,          -- 스냅샷
    quantity       INT             NOT NULL,
    line_amount    BIGINT          NOT NULL,          -- unit_price * quantity. 조회용 중복
    PRIMARY KEY (id),
    KEY idx_order_items_order_id (order_id),
    KEY idx_order_items_product_id (product_id),
    CONSTRAINT fk_order_items_order
        FOREIGN KEY (order_id) REFERENCES orders (id)
        ON DELETE RESTRICT,
    CONSTRAINT fk_order_items_product
        FOREIGN KEY (product_id) REFERENCES products (id)
        ON DELETE RESTRICT
);
```

설계 포인트 다시 정리

```
    orders.user_id
        1:N.  회원 없이 주문 불가 (FK)

    orders.order_no
        외부/고객용 번호. AUTO_INCREMENT id 를 영수증에 안 찍는다.

    order_items.product_name, unit_price
        상품 마스터가 바뀌어도 주문서가 안 바뀌게 스냅샷

    order_items.line_amount
        계산하면 나오는 값인데, 영수증/합계 검증용으로 저장 (가벼운 비정규화)

    products.price
        현재 판매가.  주문 가격이 아님. VARCHAR 가 아니라 BIGINT (원)

    엔진
        명시 안 해도 InnoDB. MyISAM 으로 바꾸지 말 것
```

조회 연습

```sql
-- 회원별 주문 수, 총 결제액
SELECT
    u.id,
    u.name,
    COUNT(o.id)            AS order_count,
    COALESCE(SUM(o.total_amount), 0) AS total_paid
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;

-- 상품이 실제로 팔린 수량 (주문 당시 기준)
SELECT
    oi.product_id,
    oi.product_name,
    SUM(oi.quantity)     AS qty,
    SUM(oi.line_amount)  AS sales
FROM order_items oi
JOIN orders o ON o.id = oi.order_id
WHERE o.status = 'paid'
GROUP BY oi.product_id, oi.product_name;
```

## 설계 체크리스트

테이블 추가하기 전에 통과시키면 된다.

- [ ] PK 는 의미 없는 `BIGINT` 인가. 이메일/휴대폰을 PK 로 쓰지 않았는가
- [ ] FK 컬럼에 인덱스가 있는가
- [ ] PK 와 FK 의 타입이 같은가 (한쪽만 VARCHAR 가 아닌가)
- [ ] 엔진이 InnoDB 인가. 메인 테이블을 MyISAM 으로 두지 않았는가
- [ ] 숫자·날짜·돈을 VARCHAR 로 넣지 않았는가. 글자만 VARCHAR 인가
- [ ] `VARCHAR(255)` 를 습관처럼 쓰지 않았는가. 길이가 의미 있는가
- [ ] 돈은 `DECIMAL` 또는 원 단위 정수인가. FLOAT 가 아닌가
- [ ] 문자셋이 `utf8mb4` 인가
- [ ] 자주 찾는 값인데 JSON/TEXT 안에만 있지는 않은가
- [ ] 마스터(상품명)와 거래(주문 당시 상품명)를 구분했는가
- [ ] 계속 쌓이는 로그를 본 테이블에 넣고 있지 않은가
- [ ] `created_at` / `updated_at` 이 있는가
- [ ] NULL 이 진짜 "없음" 을 뜻하는가. 상태값에 NULL 을 안 썼는가
- [ ] UNIQUE 가 소프트 삭제/재가입이랑 충돌하지 않는가
- [ ] 예비 컬럼, 콤마로 이은 ID 리스트가 없는가
