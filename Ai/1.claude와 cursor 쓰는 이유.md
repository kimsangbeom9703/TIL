# Claude + Cursor

> **요약**: 설계/질문은 Claude, 실제 코드 작업은 Cursor. 둘을 같이 써서 구현 속도를 올리고, 모르는 스택도 빠르게 잡아가는 방식.

## 1) 개요

**"대화로 잡고, 에디터에서 끝낸다"**

- **도구**
    - **Claude**: 설계, 원인 분석, 긴 맥락 정리, 코드 리뷰
    - **Cursor**: 프로젝트 파일을 직접 열고, 수정하고, 실행까지 하는 에디터
- **목표**: 반복 작업/보일러플레이트에 시간 쓰지 않고, 핵심 로직과 구조에 집중
- **쓰는 이유**: 거창한 건 없다. 그냥 **혼자 검색하고 삽질하는 시간**이 줄어든다.

---

## 2) Cursor를 쓰는 이유

```
VSCode 쓰듯이 쓰는데, 에디터 안에서 바로 AI한테 코드를 맡길 수 있다.

제일 큰 차이는 이것이다.
- 채팅창에 코드를 복사해서 붙여넣는 게 아니다
- 프로젝트 폴더를 보고, 파일을 직접 고친다
- 터미널, git, 검색이 한곳에 있다

실무에서 파일을 여러 개 건드려야 하는 작업이 많다.
예) NestJS 모듈 추가, Express 폴더 구조 맞추기, entity/service/controller 같이 만들기

이런 걸 채팅만으로 하면 복붙하다가 빠뜨린다.
Cursor는 워크스페이스를 보고 수정하니까 그게 덜하다.
```

---

## 3) Claude를 쓰는 이유

```
코드를 "빨리 찍어내는 것"만 필요한 게 아니다.

내가 Claude를 쓰는 포인트는 이렇다.
- 왜 이렇게 짜야 하는지 설명이 필요하다
- 구조를 먼저 잡고 싶다 (모듈 나누기, API 설계, DB 스키마)
- 에러 로그를 보고 원인을 좁히고 싶다
- 코드 리뷰처럼 "여기 위험한 부분"을 짚어줬으면 한다

그냥 자동완성만 쓰면 동작은 하는데, 왜 이렇게 됐는지 모르는 경우가 생긴다.
나중에 유지보수할 때 그게 더 힘들다.

Claude는 긴 맥락을 잘 받아서
"이 프로젝트에서는 이렇게 가는 게 맞다" 쪽으로 답을 주는 편이다.
```

---

## 4) 둘이 같이 쓰는 이유

```
역할을 나눠서 쓴다.

Claude  → 방향, 설계, 원인 분석, 리뷰
Cursor  → 실제 파일 수정, 실행, 디버깅, 커밋 전 확인

하나만 쓰면 부족하다.

Claude만 쓰면
- 코드는 나오는데 내 프로젝트에 바로 안 들어간다
- 파일 경로, 기존 코드 스타일을 매번 설명해야 한다

Cursor만 쓰면
- 빨리 고치긴 하는데, 구조를 크게 잡는 대화는 약하다
- "이게 맞나?" 하고 한 번 더 물어보기 애매하다

그래서 설계는 Claude로 잡고, 구현은 Cursor로 밀어붙인다.
```

---

## 5) 실제 작업 흐름

```
1. 뭘 만들지 먼저 짧게 정리한다
   (예: 로그인 API, 권한 가드, 관리자 페이지)

2. Claude한테 구조부터 물어본다
   - 폴더를 어떻게 나눌지
   - 테이블/엔티티는 뭐가 필요한지
   - 기존 코드랑 어떻게 맞출지

3. Cursor에서 프로젝트 열고 구현한다
   - 파일 생성 / 수정
   - 터미널에서 실행, 에러 확인

4. 막히면 에러 로그랑 관련 파일을 같이 보여준다
   - 추측하지 말고, 실제 코드 기준으로 고친다

5. 동작 확인 후 내가 한 번 더 읽는다
   - 이해 안 되는 코드는 남기지 않는다
   - 이상하면 다시 고친다

6. 나중에 까먹지 않게 TIL에 남긴다
```

## 6) 효율이 나는 부분

### 빨라지는 것

```
- 보일러플레이트
  controller / service / entity / module 같은 반복 파일

- 처음 보는 스택 진입
  NestJS, FastAPI, Electron, TypeORM 같이
  "설치 → 기본 구조 → 연동" 까지 가는 시간

- 에러 잡는 속도
  구글에 키워드 여러 번 검색하는 대신
  로그 + 코드를 같이 보고 바로 원인 좁히기

- 문서/정리
  작업하면서 바로 마크다운으로 남길 수 있다
  (지금 이 글도 그 연장선)
```

### 안 빨라지는 것 (착각하면 안 되는 부분)

```
- 요구사항이 애매하면 AI도 헤맨다
- 내가 코드를 안 읽으면 나중에 더 오래 걸린다
- 보안, 권한, 결제, 배포 같은 건 검증이 따로 필요하다
- "돌아가게 만들기"랑 "실무에서 써도 되는 코드"는 다르다
```

---

## 7) 효율을 떨어뜨리는 잘못된 사용

```
1. 질문부터 안 하고 "일단 만들어줘"만 반복
   → 결과물이 커지고, 어디가 문제인지 모름

2. 생성 코드를 그대로 커밋
   → 나중에 내가 설명 못 함

3. 프로젝트 맥락 없이 물어보기
   → 다른 스택, 다른 폴더 구조로 답을 줌

4. 한 번에 너무 많이 시키기
   → 파일은 많이 바뀌는데, 어디가 핵심 변경인지 안 보임
```

---

## 8) 내가 지키려고 하는 사용 규칙

```
- 한 번에 한 가지 작업만 시킨다
- 기존 폴더 구조/네이밍을 먼저 보여준다
- 코드를 받으면 실행하고, 직접 읽어본다
- 이해한 내용만 TIL에 남긴다
- 안 되면 전체를 다시 만들지 말고, 에러 지점만 고친다
```

---

## 9) 정리

```
Claude와 Cursor를 쓰는 이유는 단순하다.

검색 → 복붙 → 다시 검색 하는 루프를 줄이고
설계 → 구현 → 확인 루프를 빠르게 돌리기 위해서다.

효율의 핵심은 AI가 코드를 잘 짜주는 게 아니다.
내가 방향을 잡고, 결과를 검증하는 속도가 빨라지는 것이다.

못 믿겠으면 안 쓰면 된다.
쓰려면 내가 이해한 코드만 남기는 게 맞다.
```
